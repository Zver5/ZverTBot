# ZverTBot — развёртывание и перенос

Документ описывает штатный процесс сборки, переноса и развёртывания ZverTBot на новый VPS.

## Назначение

Deploy-механизм ZverTBot предназначен для повторяемого развёртывания программной части проекта на чистом сервере.

Основной принцип:
 **Переносится программная часть проекта, а runtime-состояние, секреты и инфраструктурные настройки конкретного VPS создаются заново на целевой системе.**

Это позволяет использовать один deploy-архив для установки ZverTBot на разные VPS без копирования старого рабочего окружения.

---

## Состав deploy-механизма

Основные компоненты находятся в каталоге `deploy/`:

deploy/
├── build.sh
├── output/
└── botinstaller/
    ├── install.sh
    ├── checks.sh
    ├── system_tuning.sh
    ├── packages.txt
    └── systemd/
        ├── core/
        └── optional/


Назначение компонентов:

| Компонент                                | Назначение                                 |
| ---------------------------------------- | ------------------------------------------ |
| `deploy/build.sh`                        | Сборка переносимого deploy-архива          |
| `deploy/output/`                         | Результаты сборки                          |
| `deploy/botinstaller/install.sh`         | Установка ZverTBot на целевой VPS          |
| `deploy/botinstaller/packages.txt`       | Список системных пакетов                   |
| `deploy/botinstaller/checks.sh`          | Проверки установленной системы             |
| `deploy/botinstaller/system_tuning.sh`   | Настройка IPv4-приоритета, conntrack и лимитов systemd-journald |
| `deploy/botinstaller/systemd/core/`      | Обязательные systemd-компоненты            |
| `deploy/botinstaller/systemd/optional/`  | Дополнительные эксплуатационные компоненты |

# Сборка deploy-архива

Сборка выполняется из корня проекта:

cd ~/ZverTBot
./deploy/build.sh

Сборщик:

* определяет имя проекта из конфигурации;
* определяет текущую версию ZverTBot;
* проверяет корректность версии;
* создаёт временный каталог сборки;
* копирует программную часть проекта;
* исключает Git-историю;
* исключает виртуальное окружение;
* исключает секреты;
* исключает Python-кэши;
* исключает тестовые артефакты;
* исключает runtime-состояние;
* исключает журналы и временные данные;
* отдельно добавляет корневой `.env.example` в архив как `deploy/botinstaller/.env.example`;
* формирует переносимый архив;
* подготавливает `install.sh` для установки.

Каталог `deploy/output/` используется как каталог результатов сборки и не попадает внутрь deploy-архива.

Результат находится в:
deploy/output/

Основной артефакт:
ZverTBot-deploy-VERSION.tar.gz

Установщик:
deploy/output/install.sh


---

# Состав deploy-архива

Deploy-архив содержит программную часть, необходимую для установки ZverTBot.

В архив не должны попадать данные, относящиеся к конкретному рабочему VPS.

## Исключаемые данные

Из deploy-сборки исключаются:

* `.git/`;
* `.venv/`;
* `.env`;
* Python-кэши;
* результаты тестов;
* runtime JSON-файлы;
* журналы;
* резервные копии;
* временные файлы;
* локальные эксплуатационные данные;
* `data/geoip/`;
* скрипты временных исправлений и patch-операций.

Таким образом, deploy-архив не является копией работающего `/opt/ZverTBot`.

Он представляет собой **артефакт установки программной части проекта**.

---

# Статические данные

В deploy-архив включаются необходимые файлы проекта, в том числе:

data/asn_types.json
data/ru_geo.conf
data/storage.py
data/traffic.py

Остальное содержимое `data/` не переносится как runtime-состояние.

Каталог `data/geoip/` не переносится.

GeoIP-базы устанавливаются отдельно на целевом VPS.

Это предотвращает перенос устаревших или привязанных к конкретному окружению данных.

---

# Установка на новый VPS

Для установки используются два файла:

install.sh
ZverTBot-deploy-VERSION.tar.gz

Они должны находиться в одном каталоге.

Установщик запускается от `root`.

Пример:

chmod +x install.sh
./install.sh


Установщик выполняет подготовку целевой системы, после чего устанавливает ZverTBot в:

/opt/ZverTBot


---

# Что выполняет установщик

Установщик отвечает за подготовку программного окружения ZverTBot.

Фактический порядок выполнения:

1. проверка прав `root`;
2. проверка поддерживаемой операционной системы;
3. проверка сети и DNS;
4. распаковка deploy-архива;
5. запуск `checks.sh`;
6. установка системных пакетов;
7. запуск `system_tuning.sh`;
8. создание `.env`;
9. включение IPv4 forwarding;
10. создание runtime-каталогов и начального runtime-состояния;
11. создание Python virtual environment и установка зависимостей;
12. загрузка и проверка GeoIP-баз;
13. установка systemd unit-файлов;
14. `systemctl daemon-reload`;
15. запуск и включение core и optional-компонентов;
16. базовая проверка установленных сервисов.

---

# Конфигурация

Секреты и индивидуальные параметры конкретного VPS не входят в deploy-архив.

При установке используется:
/opt/ZverTBot/.env

Если `.env` отсутствует или пустой, installer создаёт его из шаблона `deploy/botinstaller/.env.example`, который был добавлен в deploy-архив сборщиком, и подставляет параметры целевого VPS.

Если существующий `.env` непустой, installer **не перезаписывает его** и только устанавливает права `600`.

Таким образом, повторный запуск installer не должен уничтожать существующую конфигурацию.

### Обязательные параметры

Следующие параметры необходимо задать вручную для любого развёртывания:

BOT_TOKEN
ADMIN_CHAT

`SERVER_IP` также является обязательным параметром для проекта, но installer пытается определить его автоматически. Вручную задавать `SERVER_IP` требуется только при необходимости переопределить автоматически определённое значение.

### Необязательные параметры

SERVER_FLAG

Этот параметр используется как дополнительный флаг сервера и не является обязательным.

### Параметры, зависящие от окружения и используемых функций

Остальные параметры не являются обязательными для любого VPS. Их необходимость определяется используемой инфраструктурой и функциональностью конкретного развёртывания.

Инфраструктурные параметры:

HA_TUNNEL_IP
HASS_FLAG
XRAY_CONF
AWG_CONF
KUMA_HEALTHCHECK_URL

Параметры LLM:

LLM_PROVIDER
LLM_API_KEY
LLM_API_URL
LLM_MODEL
LLM_MODELS

Внешние сервисы:

ABUSEIPDB_API_KEY

Резервное копирование:

BACKUP_REMOTE
BACKUP_ROOT_DIR

Дополнительные runtime-параметры:

ZVERTBOT_LOG_LEVEL

Installer пытается автоматически определить параметры инфраструктуры там, где это предусмотрено. Остальные параметры задаются только при использовании соответствующего функционала.

`.env.example` содержит шаблон конфигурации без секретов конкретного VPS.

Файл `.env` должен иметь права `600`, поскольку содержит секреты и серверные параметры.

Это обеспечивает разделение:

Deploy archive
    │
    ├── код
    ├── services
    ├── handlers
    ├── scripts
    └── systemd templates

Target environment
    │
    ├── .env
    ├── VPN configuration
    ├── IP addresses
    ├── secrets
    └── runtime state

# Xray

Конфигурация Xray относится к инфраструктуре целевого VPS.

Установщик не должен предполагать фиксированный путь к конфигурации.

Для определения конфигурации используется systemd-служба `xray.service`.

Установщик пытается автоматически определить путь к конфигурационному файлу через `ExecStart` и сохранить его в `XRAY_CONF`.

Если определить путь не удалось, `XRAY_CONF` остаётся пустым и installer выводит предупреждение.

Таким образом, deploy-архив не содержит конфигурацию Xray конкретного сервера.

---

# AmneziaWG

Конфигурация AmneziaWG относится к инфраструктуре целевого VPS.

Deploy-механизм не переносит рабочую конфигурацию AmneziaWG со старого сервера как runtime-файл.

Installer пытается определить конфигурацию AmneziaWG по существующим systemd unit-файлам `awg-quick@*.service`.

Если путь к конфигурации удалось определить, он сохраняется в `AWG_CONF`.

Если определить путь не удалось, `AWG_CONF` может остаться пустым и installer выводит предупреждение.

Это позволяет отделить:

* программную часть ZverTBot;
* конфигурацию конкретного VPN-сервера;
* runtime-состояние клиентов.

---

# GeoIP

GeoIP-базы не входят в deploy-архив.

Они загружаются установщиком на целевом VPS.

При подготовке базы выполняются проверки:

* доступности загрузки;
* корректности gzip-архива;
* валидности полученной MMDB;
* возможности использования базы библиотекой `maxminddb`.

Установщик сначала проверяет текущий месячный релиз DB-IP Lite, затем при необходимости предыдущий месяц. Уже существующая непустая база повторно не скачивается.

GeoIP-базы являются внешними обновляемыми данными и поэтому не должны храниться внутри deploy-артефакта проекта.

---

# Systemd

Systemd-конфигурация ZverTBot разделена на две категории:
deploy/botinstaller/systemd/
├── core/
└── optional/

## Core

Core-компоненты являются основной частью эксплуатационного контура ZverTBot.

В штатной установке используются:

zvertbot.service
stats-http.service
vps-stats.service
vps-stats.timer
geoip-collect.timer
healthcheck.service

## Optional

Дополнительные компоненты устанавливаются при наличии соответствующих unit-файлов:

xray-traffic.service
xray-traffic.timer
zvertbot-backup.service
zvertbot-backup.timer
kuma-webhook.service

`xray-traffic.timer` запускает `xray-traffic.service`, а `zvertbot-backup.timer` запускает `zvertbot-backup.service`. Эти service-unit'ы устанавливаются как часть optional-контура и выполняются по соответствующим таймерам.

Backup-механизм использует параметры `BACKUP_REMOTE` и `BACKUP_ROOT_DIR`, поэтому конкретный тип remote определяется конфигурацией целевого VPS.


После установки systemd-конфигурация перечитывается: systemctl daemon-reload


После этого соответствующие службы и таймеры включаются и запускаются согласно их назначению.

Состояние VPS контролируется через healthcheck.service. Healthcheck проверяет основные сервисы и инфраструктурные зависимости, включая SSH-туннель HA при заданном HA_TUNNEL_IP.

Uptime Kuma использует HTTP endpoint healthcheck и отслеживает его состояние. При переходе состояния Kuma вызывает kuma-webhook.service, который отправляет уведомление в Telegram и при деградации healthcheck может включать подробности обнаруженных проблем.

Конфигурации внешних инфраструктурных сервисов, таких как Xray и AmneziaWG, не являются частью списка core-служб ZverTBot.

---

# Проверка установки

Установщик выполняет базовую автоматическую проверку установленной системы.

Проверяются основные компоненты:

zvertbot.service
healthcheck.service
stats-http.service
vps-stats.timer
geoip-collect.timer

Для таймеров дополнительно проверяется их включение.

После установки можно выполнить ручную проверку:

systemctl status zvertbot.service
systemctl status stats-http.service
systemctl status healthcheck.service
systemctl status vps-stats.timer
systemctl status geoip-collect.timer

Проверка Python-окружения:

cd /opt/ZverTBot
.venv/bin/python --version

При необходимости состояние systemd можно проверить отдельно: systemctl --failed

Optional-компоненты, VPN-инфраструктура и эксплуатационные функции проверяются в соответствии с конфигурацией конкретного VPS.

# Перенос существующего VPS

Перенос ZverTBot на новый сервер не выполняется копированием всего старого каталога:

/opt/ZverTBot

Вместо этого создаётся новый deploy-архив.

Штатный процесс:

Старый VPS / рабочая копия
          │
          ▼
   deploy/build.sh
          │
          ▼
ZverTBot-deploy-VERSION.tar.gz
          │
          ▼
      Новый VPS
          │
          ▼
      install.sh
          │
          ▼
    /opt/ZverTBot
          │
          ├── .venv
          ├── .env
          ├── systemd
          └── runtime state

Такой подход позволяет заново создать окружение целевого сервера вместо переноса состояния старого VPS.

---

# Что намеренно не переносится

При переносе не копируются:

* Git-история;
* `.venv`;
* секреты;
* `.env`;
* старые журналы;
* runtime-кэш;
* временные файлы;
* старые GeoIP-базы;
* резервные копии;
* локальное runtime-состояние старого сервера;
* конфигурации инфраструктуры, специфичные для старого VPS.

Runtime-файлы на новом сервере создаются заново. К ним относятся registry AWG-клиентов, bindings Telegram-пользователей, tickets, IP-токены и runtime-снимки HASS.

Если эти данные необходимо сохранить, их следует отдельно восстановить из резервной копии.

Это снижает зависимость нового сервера от состояния исходного окружения.

---

# Принцип переносимости

Deploy-архив должен содержать только компоненты, необходимые для установки программной части ZverTBot.

Инфраструктурные параметры определяются отдельно на целевом VPS.

К таким параметрам относятся:

* IP-адрес сервера;
* пути к конфигурации Xray;
* пути к конфигурации AmneziaWG;
* сетевые интерфейсы;
* systemd-окружение;
* секреты;
* GeoIP-базы;
* параметры Home Assistant;
* параметры внешнего мониторинга;
* другие параметры, зависящие от конкретной инфраструктуры.

Главное требование:

> **Один deploy-архив должен быть пригоден для повторной установки ZverTBot на другой совместимый VPS без копирования состояния исходного сервера.**

---

# Рекомендуемый процесс обновления

Для подготовки новой версии:

cd ~/ZverTBot
./deploy/build.sh

После успешной сборки необходимо проверить содержимое: deploy/output/

На целевой системе используется соответствующий: install.sh и ZverTBot-deploy-VERSION.tar.gz

После установки рекомендуется проверить:

systemctl status zvertbot.service
systemctl status stats-http.service
systemctl status healthcheck.service

а также состояние таймеров:

systemctl status vps-stats.timer
systemctl status geoip-collect.timer

---

# Результат развёртывания

После успешной установки целевой VPS должен содержать:

* установленный ZverTBot в `/opt/ZverTBot`;
* рабочее Python-окружение;
* установленные системные зависимости;
* конфигурацию `.env`;
* необходимые systemd-компоненты;
* подготовленное runtime-окружение;
* актуальные GeoIP-базы;
* подключённые VPN-компоненты целевой инфраструктуры;
* необходимые эксплуатационные службы и таймеры.

Deploy-механизм обеспечивает **повторяемое развёртывание ZverTBot с нуля** и перенос проекта между VPS без ручного копирования runtime-состояния исходного сервера.
