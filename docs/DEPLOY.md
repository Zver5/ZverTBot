# ZverTBot — развёртывание и перенос

Документ описывает штатный процесс сборки, переноса и развёртывания ZverTBot на новый VPS.

## Назначение

Deploy-механизм ZverTBot предназначен для повторяемого развёртывания программной части проекта на чистом сервере.

Основной принцип:

> **Переносится программная часть проекта, а runtime-состояние, секреты и инфраструктурные настройки конкретного VPS создаются заново на целевой системе.**

Это позволяет использовать один deploy-архив для установки ZverTBot на разные VPS без копирования старого рабочего окружения.

---

## Состав deploy-механизма

Основные компоненты находятся в каталоге `deploy/`:

```text
deploy/
├── build.sh
├── output/
└── botinstaller/
    ├── install.sh
    ├── checks.sh
    ├── system_tuning.sh
    ├── packages.txt
    ├── .env.example
    ├── examples/
    │   ├── awg0.conf.example
    │   └── xray.config.example.json
    └── systemd/
        ├── core/
        └── optional/
```

Назначение компонентов:

| Компонент                               | Назначение                                                      |
| --------------------------------------- | --------------------------------------------------------------- |
| `deploy/build.sh`                       | Сборка переносимого deploy-архива                               |
| `deploy/output/`                        | Результаты сборки                                               |
| `deploy/botinstaller/install.sh`        | Установка ZverTBot на целевой VPS                               |
| `deploy/botinstaller/packages.txt`      | Список системных пакетов                                        |
| `deploy/botinstaller/checks.sh`         | Проверки установленной системы                                  |
| `deploy/botinstaller/system_tuning.sh`  | Настройка IPv4-приоритета, conntrack и лимитов systemd-journald |
| `deploy/botinstaller/.env.example`      | Шаблон конфигурации ZverTBot                                    |
| `deploy/botinstaller/examples/`         | Шаблоны конфигураций Xray и AmneziaWG                           |
| `deploy/botinstaller/systemd/core/`     | Основные systemd-компоненты                                     |
| `deploy/botinstaller/systemd/optional/` | Дополнительные эксплуатационные компоненты                      |

# Сборка deploy-архива

Сборка выполняется из корня проекта:

```bash
cd ~/ZverTBot
./deploy/build.sh
```

Сборщик:

* определяет имя проекта из конфигурации;
* определяет текущую версию ZverTBot;
* проверяет корректность версии;
* создаёт временный каталог сборки;
* копирует программную часть проекта;
* исключает Git-историю;
* исключает виртуальное окружение;
* исключает секреты;
* исключает Python-кэши;
* исключает тестовые артефакты;
* исключает runtime-состояние;
* исключает журналы и временные данные;
* отдельно добавляет корневой `.env.example` в архив как `deploy/botinstaller/.env.example`;
* включает шаблоны конфигураций Xray и AmneziaWG;
* формирует переносимый архив;
* подготавливает `install.sh` для установки.

Каталог `deploy/output/` используется как каталог результатов сборки и не попадает внутрь deploy-архива.

Результат находится в:

```text
deploy/output/
```

Основной артефакт:

```text
ZverTBot-deploy-VERSION.tar.gz
```

Установочный скрипт:

```text
deploy/output/install.sh
```

# Состав deploy-архива

Deploy-архив содержит программную часть, необходимую для установки ZverTBot.

В архив не должны попадать данные, относящиеся к конкретному рабочему VPS.

## Исключаемые данные

Из deploy-сборки исключаются:

* `.git/`;
* `.venv/`;
* `.env`;
* Python-кэши;
* результаты тестов;
* runtime JSON-файлы;
* журналы;
* резервные копии;
* временные файлы;
* локальные эксплуатационные данные;
* `data/geoip/`;
* скрипты временных исправлений и patch-операций.

Таким образом, deploy-архив не является копией работающего `/opt/ZverTBot`.

Он представляет собой **артефакт установки программной части проекта**.

---

# Статические данные

В deploy-архив включаются необходимые файлы проекта, в том числе:

```text
data/asn_types.json
data/ru_geo.conf
data/storage.py
data/traffic.py
```

Остальное содержимое `data/` не переносится как runtime-состояние.

Каталог `data/geoip/` не переносится.

GeoIP-базы устанавливаются отдельно на целевом VPS.

Это предотвращает перенос устаревших или привязанных к конкретному окружению данных.

# Установка на новый VPS

Установка выполняется от имени `root`.

Для установки используются:

```text
install.sh
ZverTBot-deploy-VERSION.tar.gz
```

Они должны находиться в одном каталоге.

Перед запуском необходимо сделать установщик исполняемым:

```bash
chmod +x install.sh
```

## Базовая установка

Установка только ZverTBot:

```bash
./install.sh
```

## Установка с Xray

```bash
./install.sh -xray
```

В этом режиме installer дополнительно устанавливает Xray и подготавливает инфраструктуру для его использования ZverTBot.

## Установка с AmneziaWG

```bash
./install.sh -awg
```

В этом режиме installer дополнительно устанавливает AmneziaWG.

## Установка с Xray и AmneziaWG

```bash
./install.sh -xray -awg
```

Это полный вариант установки с обоими VPN-компонентами.

### Важно

Ключи `-xray` и `-awg` являются **опциональными**.

Без соответствующего ключа installer не должен устанавливать соответствующий VPN-компонент.

Установка Xray или AmneziaWG не означает, что серверная VPN-конфигурация автоматически становится готовой к выдаче клиентских конфигураций. Рабочая конфигурация должна соответствовать требованиям соответствующего сервиса.

---

# Важное ограничение по тестированию installer

`install.sh` изменяет системное окружение VPS: устанавливает пакеты, systemd units, Python-окружение и дополнительные компоненты.

Поэтому installer **не следует запускать для проверки на основном production VPS**.

Проверка установочного сценария должна выполняться на отдельной тестовой машине или временном VPS.

На production-сервере допускаются:

* чтение исходного кода;
* статические проверки;
* unit-тесты;
* тесты с mock/temp-каталогами;
* проверки deploy-архива, не изменяющие систему.

---

# Что выполняет установщик

Установщик отвечает за подготовку программного окружения ZverTBot.

Фактический порядок выполнения включает:

1. проверку прав `root`;
2. проверку поддерживаемой операционной системы;
3. проверку сети и DNS;
4. распаковку deploy-архива;
5. запуск `checks.sh`;
6. установку системных пакетов;
7. запуск `system_tuning.sh`;
8. создание `.env`;
9. включение IPv4 forwarding;
10. создание runtime-каталогов и начального runtime-состояния;
11. создание Python virtual environment и установку зависимостей;
12. загрузку и проверку GeoIP-баз;
13. установку systemd unit-файлов;
14. `systemctl daemon-reload`;
15. запуск и включение core и optional-компонентов;
16. при использовании `-xray` — установку и подготовку Xray;
17. при использовании `-awg` — установку и подготовку AmneziaWG;
18. определение путей конфигурации VPN-компонентов;
19. базовую проверку установленных сервисов.

# Конфигурация

Секреты и индивидуальные параметры конкретного VPS не входят в deploy-архив.

При установке используется:

```text
/opt/ZverTBot/.env
```

Если `.env` отсутствует или пустой, installer создаёт его из шаблона:

```text
deploy/botinstaller/.env.example
```

Этот шаблон добавляется в deploy-архив сборщиком.

При создании `.env` installer подставляет параметры целевого VPS там, где автоматическое определение предусмотрено.

Если существующий `.env` непустой, installer **не перезаписывает его** и только устанавливает права `600`.

Таким образом, повторный запуск installer не должен уничтожать существующую конфигурацию.

---

# Переменные `.env`

## Обязательные параметры

Следующие параметры необходимо задать вручную для любого развёртывания:

```text
BOT_TOKEN
ADMIN_CHAT
```

`SERVER_IP` также является обязательным параметром проекта, однако installer пытается определить его автоматически.

Вручную задавать `SERVER_IP` требуется только при необходимости переопределить автоматически определённое значение.

---

## Дополнительные параметры

```text
SERVER_FLAG
```

Используется как дополнительный флаг сервера и не является обязательным.

---

## Инфраструктурные параметры

```text
HA_TUNNEL_IP
HASS_FLAG
XRAY_CONF
AWG_CONF
```

Не все эти параметры обязательны для каждого VPS.

Installer пытается автоматически определить параметры инфраструктуры там, где это предусмотрено.

---

## Параметры LLM

```text
LLM_PROVIDER
LLM_API_KEY
LLM_API_URL
LLM_MODEL
LLM_MODELS
```

Используются только при соответствующем функционале LLM.

---

## Внешние сервисы

```text
ABUSEIPDB_API_KEY
```

Используется при подключении соответствующей функциональности AbuseIPDB.

---

## Резервное копирование

```text
BACKUP_REMOTE
BACKUP_ROOT_DIR
```

Эти параметры определяют rclone remote и корневой каталог резервных копий.

Пример:

```text
BACKUP_REMOTE=yandex
BACKUP_ROOT_DIR=VPS
```

При такой конфигурации архивы конфигурации сохраняются в:

```text
yandex:VPS/configs/
```

а паспортные данные — в:

```text
yandex:VPS/passport/
```

Конкретный тип удалённого хранилища определяется настройкой rclone remote, а не самим скриптом резервного копирования.

---

## Дополнительные runtime-параметры

```text
ZVERTBOT_LOG_LEVEL
```

Позволяет изменить уровень журналирования ZverTBot.

# Xray

Xray является дополнительным компонентом deploy-механизма и устанавливается только при использовании:

```bash
./install.sh -xray
```

или:

```bash
./install.sh -xray -awg
```

## Определение конфигурации

Конфигурация Xray относится к инфраструктуре целевого VPS.

Installer не предполагает фиксированный путь к конфигурации.

После установки Xray installer анализирует:

```text
xray.service
```

и пытается определить путь к конфигурационному файлу через `ExecStart`.

Обнаруженный путь сохраняется в:

```text
XRAY_CONF
```

Если определить путь не удалось, `XRAY_CONF` может остаться пустым, а installer выводит предупреждение.

---

## Example-конфигурация Xray

В deploy-пакет входит шаблон:

```text
deploy/botinstaller/examples/xray.config.example.json
```

Он используется как **пример структуры конфигурации**, если стандартный конфигурационный файл Xray отсутствует.

Шаблон содержит значения вида:

```text
REPLACE_WITH_XRAY_REALITY_PRIVATE_KEY
REPLACE_WITH_REALITY_SHORT_ID
```

и примерные параметры `serverNames`.

Это **не готовая рабочая конфигурация**.

Перед использованием необходимо заменить все шаблонные значения на реальные параметры сервера.

---

## Проверка готовности Xray

Наличие файла конфигурации само по себе не означает, что Xray готов к созданию клиентов.

Перед созданием VLESS-клиента ZverTBot проверяет готовность конфигурации.

Проверяются, в частности:

* наличие VLESS inbound;
* наличие `settings`;
* наличие списка `clients`;
* наличие `streamSettings`;
* `network = tcp`;
* `security = reality`;
* наличие `realitySettings`;
* наличие реального `privateKey`;
* отсутствие шаблонного `REPLACE_WITH_*` private key;
* наличие `serverNames`;
* наличие `shortIds`.

Пустой список клиентов допустим: новый сервер может быть установлен без существующих VLESS-клиентов.

Если конфигурация не готова, создание клиента блокируется и администратору возвращается список обнаруженных проблем.

Это предотвращает создание некорректных VLESS-конфигураций на неподготовленном сервере.

# AmneziaWG

AmneziaWG является дополнительным компонентом и устанавливается только при использовании:

```bash
./install.sh -awg
```

или:

```bash
./install.sh -xray -awg
```

## Определение конфигурации

Рабочая конфигурация AmneziaWG относится к инфраструктуре целевого VPS.

Installer не переносит рабочую конфигурацию AmneziaWG со старого сервера.

После установки installer пытается определить конфигурацию через существующие systemd units:

```text
awg-quick@*.service
```

и соответствующие конфигурационные файлы.

Обнаруженный путь сохраняется в:

```text
AWG_CONF
```

Если путь определить не удалось, `AWG_CONF` может остаться пустым, а installer выводит предупреждение.

---

## Example-конфигурация AmneziaWG

В deploy-пакет входит шаблон:

```text
deploy/botinstaller/examples/awg0.conf.example
```

Если стандартный конфигурационный файл отсутствует, installer может установить этот шаблон в:

```text
/etc/amnezia/amneziawg/awg0.conf
```

Шаблон содержит значения вида:

```text
REPLACE_WITH_AWG_SERVER_PRIVATE_KEY
REPLACE_WITH_CLIENT_PUBLIC_KEY
```

Это **не готовая рабочая конфигурация**.

Перед использованием необходимо заменить шаблонные значения на реальные ключи и параметры сервера.

---

## Проверка готовности AmneziaWG

Перед созданием AWG-клиента ZverTBot проверяет серверную конфигурацию.

Проверяются:

* наличие `[Interface]`;
* наличие `PrivateKey`;
* отсутствие шаблонного `REPLACE_WITH_*` private key;
* наличие `Address`;
* наличие `ListenPort`.

Список существующих Peer может быть пустым — это допустимо для нового сервера.

Если конфигурация не готова, создание клиента блокируется и администратору возвращается список обнаруженных проблем.

---

# Важное различие между установкой VPN и готовностью VPN

Установка:

```bash
./install.sh -xray -awg
```

означает установку программных компонентов Xray и AmneziaWG.

Она **не означает**, что VPN полностью настроен.

После установки необходимо отдельно подготовить рабочие конфигурации:

```text
Xray
    ├── Reality private key
    ├── shortIds
    ├── serverNames
    └── VLESS inbound

AmneziaWG
    ├── server private key
    ├── Address
    ├── ListenPort
    └── параметры конкретной VPN-инфраструктуры
```

Только после подготовки конфигураций соответствующий компонент считается готовым к созданию клиентов.

# GeoIP

GeoIP-базы не входят в deploy-архив.

Они загружаются установщиком на целевой VPS.

При подготовке базы выполняются проверки:

* доступности загрузки;
* корректности gzip-архива;
* валидности полученной MMDB;
* возможности использования базы библиотекой `maxminddb`.

Установщик сначала проверяет текущий месячный релиз DB-IP Lite, затем при необходимости предыдущий месяц.

Уже существующая непустая база повторно не скачивается.

GeoIP-базы являются внешними обновляемыми данными и поэтому не должны храниться внутри deploy-артефакта проекта.

# Systemd

Systemd-конфигурация ZverTBot разделена на две категории:

```text
deploy/botinstaller/systemd/
├── core/
└── optional/
```

## Core

Core-компоненты являются основной частью эксплуатационного контура ZverTBot.

В штатной установке используются:

```text
zvertbot.service
zvertbot-vps-monitor.service
stats-http.service
vps-stats.service
vps-stats.timer
geoip-collect.timer
```

## Optional

Дополнительные компоненты:

```text
xray-traffic.service
xray-traffic.timer
zvertbot-backup.service
zvertbot-backup.timer
```

`xray-traffic.timer` запускает `xray-traffic.service`.

`zvertbot-backup.timer` запускает `zvertbot-backup.service`.

Эти компоненты относятся к optional-контуру и используются при наличии соответствующей конфигурации и функциональности.

# Резервное копирование

Backup-механизм использует:

```text
BACKUP_REMOTE
BACKUP_ROOT_DIR
```

Удалённый путь для архивов:

```text
${BACKUP_REMOTE}:${BACKUP_ROOT_DIR}/configs/
```

Паспортные данные:

```text
${BACKUP_REMOTE}:${BACKUP_ROOT_DIR}/passport/
```

Перед загрузкой проверяется наличие настроенного rclone remote.

Если remote не настроен или недоступен, backup может быть создан локально, но удалённая копия не считается успешно сохранённой.

## Загрузка backup

Для ручного запуска через Telegram используется единое сообщение с обновлением состояния.

Сначала отображается:

```text
📦 Создание архива, ожидайте...
```

Во время загрузки отображается реальный прогресс rclone:

```text
🔄 Загрузка бэкапа

☁️ Загрузка на backup remote
[██████████████░░░░░░] 74%

📦 58.3 / 78.2 MB
⚡ 12.3 MB/s
⏳ Осталось: 1 сек
```

Процент, размер, скорость и ETA берутся из реального вывода rclone.

После завершения то же сообщение заменяется итоговым результатом.

Дополнительное промежуточное сообщение «загрузка завершена» не создаётся.

# Проверка установки

Установщик выполняет базовую автоматическую проверку установленной системы.

Проверяются основные компоненты:

```text
zvertbot.service
zvertbot-vps-monitor.service
stats-http.service
vps-stats.timer
geoip-collect.timer
```

Для таймеров дополнительно проверяется их включение.

После установки можно выполнить ручную проверку:

```bash
systemctl status zvertbot.service
systemctl status zvertbot-vps-monitor.service
systemctl status stats-http.service
systemctl status vps-stats.timer
systemctl status geoip-collect.timer
```

Проверка Python-окружения:

```bash
cd /opt/ZverTBot
.venv/bin/python --version
```

При необходимости состояние systemd можно проверить отдельно:

```bash
systemctl --failed
```

Optional-компоненты, Xray, AmneziaWG и эксплуатационные функции проверяются в соответствии с конфигурацией конкретного VPS.

# Перенос существующего VPS

Перенос ZverTBot на новый сервер не выполняется копированием всего старого каталога:

```text
/opt/ZverTBot
```

Вместо этого создаётся новый deploy-архив.

Штатный процесс:

```text
Старый VPS / рабочая копия
          │
          ▼
   deploy/build.sh
          │
          ▼
ZverTBot-deploy-VERSION.tar.gz
          │
          ▼
      Новый VPS
          │
          ▼
      install.sh
          │
          ├── ZverTBot
          ├── Xray (опционально)
          └── AmneziaWG (опционально)
          │
          ▼
    /opt/ZverTBot
          │
          ├── .venv
          ├── .env
          ├── systemd
          └── runtime state
```

Такой подход позволяет заново создать окружение целевого сервера вместо переноса состояния старого VPS.

# Что намеренно не переносится

При переносе не копируются:

* Git-история;
* `.venv`;
* секреты;
* `.env`;
* старые журналы;
* runtime-кэш;
* временные файлы;
* старые GeoIP-базы;
* резервные копии;
* локальное runtime-состояние старого сервера;
* рабочие конфигурации Xray;
* рабочие конфигурации AmneziaWG;
* сетевые параметры, специфичные для старого VPS.

Runtime-файлы на новом сервере создаются заново.

К ним относятся:

* registry AWG-клиентов;
* bindings Telegram-пользователей;
* tickets;
* IP-токены;
* runtime-снимки HASS;
* другие эксплуатационные данные.

Если эти данные необходимо сохранить, их следует отдельно восстановить из резервной копии.

Это снижает зависимость нового сервера от состояния исходного окружения.

# Принцип переносимости

Deploy-архив должен содержать только компоненты, необходимые для установки программной части ZverTBot.

Инфраструктурные параметры определяются отдельно на целевом VPS.

К таким параметрам относятся:

* IP-адрес сервера;
* пути к конфигурации Xray;
* пути к конфигурации AmneziaWG;
* сетевые интерфейсы;
* systemd-окружение;
* секреты;
* GeoIP-базы;
* параметры Home Assistant;
* параметры внешнего мониторинга;
* параметры rclone;
* другие параметры, зависящие от конкретной инфраструктуры.

Главное требование:

> **Один deploy-архив должен быть пригоден для повторной установки ZverTBot на другой совместимый VPS без копирования состояния исходного сервера.**

# Рекомендуемый процесс обновления

Для подготовки новой версии:

```bash
cd ~/ZverTBot
./deploy/build.sh
```

После успешной сборки необходимо проверить содержимое:

```text
deploy/output/
```

Основной артефакт:

```text
ZverTBot-deploy-VERSION.tar.gz
```

На целевой системе используются:

```text
install.sh
ZverTBot-deploy-VERSION.tar.gz
```

При необходимости VPN-компонентов используются соответствующие ключи:

```bash
./install.sh -xray
```

или:

```bash
./install.sh -awg
```

или:

```bash
./install.sh -xray -awg
```

После установки рекомендуется проверить:

```bash
systemctl status zvertbot.service
systemctl status stats-http.service
systemctl status zvertbot-vps-monitor.service
```

а также состояние таймеров:

```bash
systemctl status vps-stats.timer
systemctl status geoip-collect.timer
```

Если используются VPN-компоненты, дополнительно необходимо проверить:

* наличие `XRAY_CONF` / `AWG_CONF`;
* состояние соответствующих systemd-служб;
* готовность рабочих конфигураций;
* отсутствие шаблонных `REPLACE_WITH_*` значений;
* возможность создания клиента.

# Результат развёртывания

После успешной установки целевой VPS должен содержать:

* установленный ZverTBot в `/opt/ZverTBot`;
* рабочее Python-окружение;
* установленные системные зависимости;
* конфигурацию `.env`;
* необходимые systemd-компоненты;
* подготовленное runtime-окружение;
* актуальные GeoIP-базы;
* при необходимости установленный Xray;
* при необходимости установленный AmneziaWG;
* определённые пути `XRAY_CONF` / `AWG_CONF`, если соответствующие конфигурации обнаружены;
* настроенные VPN-конфигурации целевой инфраструктуры;
* необходимые эксплуатационные службы и таймеры.

При использовании Xray и/или AmneziaWG необходимо помнить:

> **Установка программного компонента и готовность его конфигурации — разные этапы.**

ZverTBot блокирует создание VPN-клиентов, если соответствующая конфигурация не прошла readiness-проверку.

Deploy-механизм обеспечивает **повторяемое развёртывание ZverTBot с нуля** и перенос проекта между VPS без ручного копирования runtime-состояния исходного сервера.
